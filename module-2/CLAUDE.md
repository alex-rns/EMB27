## What to watch for (common mistakes, including in AI-generated code)

- **`volatile`:** needed for data an ISR writes and `loop()` reads, and for hardware registers. It gives no
  atomicity: a value wider than 32 bits, `counter++` or a read-and-clear can be cut by an interrupt between two
  accesses (see 1.5 in `../module-1/CLAUDE.md`).
- **ISR rules from module 1 still hold:** short, no `delay`, no `Serial`, `attachInterrupt` last in `setup()`
  (`../module-1/CLAUDE.md`, 1.5).
- **Time arithmetic:** `now - last >= interval` with `uint32_t` survives the `millis()` wrap; `now >= last + interval`
  and signed types don't.
- **`constexpr` and memory:** a global `constexpr` table lands in flash (`.rodata`); a local one inside a function
  can be rebuilt on the stack on every call unless it is `static constexpr`. Check with `nm`/`size`, not by belief.
- **Hardware in constructors:** a global object's constructor runs before `setup()`; pin setup belongs in an explicit
  `init()` called from `setup()`.
- **Hidden heap:** Arduino's `String`, `WebServer` and Wi-Fi allocate; the lesson's "no dynamic memory" rule covers
  our code, not the core.
- **Register addresses differ per chip:** an address copied from another MCU's example reads something else.
  STM32F411: `GPIOA` base `0x40020000` is `MODER` (modes); the input levels are `IDR` at offset `0x10` (RM0383 §8.4.5).

## Lesson notes

### 2.1 — Embedded C++ blink (`2.1-embedded-cpp`)

Steps: `00-practice-blink-esp32` (the homework tasks done before the lecture) and `01-homework-blink-esp32` (the
homework, PR #6: one folder, one commit per change). The two have the same code. No Wokwi circuit or schematic for
this lesson. Pins: LED 7, button 9. `01-homework-blink-stm32` (PR #7) does the required tasks 1 and 2 on the Black
Pill; the optional 3 and 4 are ESP32 only. The lesson README gets its link in row `01` after both PRs are merged
(changing that row in both PRs would make them conflict).

- **`enum class LedState { On, Off }`:** no implicit conversion to an integer, so `digitalWrite(pin, state)` doesn't
  compile; `Led::set()` maps it with `state == LedState::On ? HIGH : LOW`. Enumerators named `HIGH` / `LOW` clash
  with Arduino's macros (`#define HIGH 0x1`, `esp32-hal-gpio.h`). Without an underlying type it takes 4 bytes.
- **`struct Config` with `static constexpr` members:** a non-static `constexpr` data member doesn't compile. The values
  cost no memory: `nm -C -S firmware.elf` shows no `Config::` symbol at all, the numbers sit in the instructions.
- **`static` locals in `loop()`** keep their value between calls and are visible only inside `loop()`. Zero-initialised
  ones land in `.bss`; `ledState` starts at `LedState::Off` (= 1), so it lands in `.data` (`nm`: `d`, not `b`). The
  initializer runs once: `static uint32_t now = millis();` would freeze the time of the first call.
- **Pin setup in `Led::init()`, not in the constructor:** the global `led` is constructed before `setup()` runs (C++
  static initialization in the startup code).
- **Loop timing:** `micros()` around the loop's work, the print kept out of the measured part. Average 2.03–2.05 µs with
  the blink only, 2.12–2.16 µs with the button logic. `micros()` counts whole microseconds, so a single iteration reads
  as 2 or 3 µs and the average of 1000 gives the fraction. `Serial` adds about 24 KB of flash and 360 bytes of RAM.
- **Button:** the `IRAM_ATTR` ISR only sets a `volatile bool`; `loop()` clears it and accepts a press 30 ms or more
  after the previous one, then moves the mode on with `nextMode()`. The read and the clear of the flag are two steps,
  not one atomic action.
- **Toolchain:** the ESP32-S3 Arduino core 2.0.17 builds with GCC 8.4.0 and `-std=gnu++11`, so `std::make_unique` and
  `std::optional` are missing; `std::array` compiles.

STM32 version (`01-homework-blink-stm32`), what differs:

- **C++ in a CubeMX project:** right-click the project → Convert to C++ (g++ for `.cpp`, g++ as the linker). `main.c`
  stays C and only calls `app_setup()` / `app_loop()` from its `USER CODE` blocks; `app.h` declares them inside
  `extern "C"` (`#ifdef __cplusplus` guards), otherwise `main.c` looks for `app_setup` while `app.cpp` defines
  `_Z9app_setupv`. Our code lives in `app.cpp`, `config.h`, `led.h`.
- **A new `.cpp` needs one CubeIDE build:** CubeIDE writes `Debug/*.mk` from the files it sees; a terminal build
  (`make -C Debug`) with older makefiles skips the file and fails to link (`undefined reference to 'app_setup'`).
  New headers need nothing.
- **The pin is a mask:** `GPIO_PIN_13` is `((uint16_t)0x2000)`. A `uint8_t` truncates it to 0 (`-Woverflow`, the build
  still succeeds) and `HAL_GPIO_WritePin` then writes 0 to `BSRR`: no pin changes, the LED stays lit, and nothing
  reports it (`USE_FULL_ASSERT` is off). A pin number such as `7` compiles silently and selects PC0–PC2.
- **The port in `Config`:** `GPIOC` can't be `constexpr` (open 1). Used: `static GPIO_TypeDef* ledPort() { return GPIOC; }`,
  20 bytes at `-O0`, inlined at `-O2`. A `static GPIO_TypeDef* const` member works too but needs an out-of-class
  definition in C++14; `const GPIO_TypeDef*` (pointer to read-only registers) is rejected by `HAL_GPIO_WritePin`.
- **Pin setup is CubeMX's:** `MX_GPIO_Init()` sets the mode and writes PC13 low first (LED on at reset), so
  `Led::init()` only sets the starting state (off); `set(LedState::On)` writes `GPIO_PIN_RESET`.
- **Build:** `text` 5960, `data` 16, `bss` 1576 (Debug, `-O0`; `bss` includes 1536 bytes of `._user_heap_stack`).
  0 warnings with CubeIDE's `-Wall`; `app.cpp` and `main.c` compiled by hand with `-Wextra` give none either.

### 2.2 — Passive and active loads (`2.2-passive-active-loads`)

Steps: `00-homework-relay-delay-esp32` (PR #10, ESP-IDF in C), `00-homework-relay-delay-stm32` (PR #11) and the bonus
`01-homework-soft-pwm-stm32` (PR #12). The READMEs hold the details; what to remember:

- **The relay module's own PNP input stage** (emitter on 5 V) never turns off from a 3.3 V high: the BC547 with a
  10 kΩ pull-up to 5 V on `IN` gives it a full 0 / 5 V swing, on both boards.
- **STM32 relay timing:** TIM2 at 1 MHz, PB1 polled with `HAL_GPIO_ReadPin` (the teacher accepted polling or EXTI).
  Results with the same relay: ON ≈ 3.3 ms, OFF ≈ 4.1 ms on both boards. A cycle is skipped when the contact starts in
  the wrong state or doesn't change within 50 ms: power cuts during the test produced a false "1 us" and a 0.55 s ON
  before those checks.
- **`printf` on the STM32** needs our own `__io_putchar` (a weak symbol in `syscalls.c`; without it the call is
  linked as a no-op and nothing appears). The steps use `snprintf` + `HAL_UART_Transmit` instead, and `%lu` for
  `uint32_t`. `snprintf` costs about 3.4 KB of flash.
- **Soft PWM:** `HAL_GetTick() % 10` against `duty_ms` (100 Hz, 11 levels), no `HAL_Delay`. Buttons on edges, each
  with its own debounce on both edges (30 ms after the last accepted change); without it one press moved two steps.
  `duty_ms > 0` before `--` (unsigned wrap). Resistors: LED 220 Ω (8.2 mA from 5 V, blue Vf ≈ 3 V), base 1 kΩ
  (2.6 mA, forced β 10 needs 0.82 mA).
- **A button that never reads 0:** check the legs (diagonal legs are always on different pairs), then read `IDR`,
  `MODER`, `PUPDR` through the ST-Link (`stm32 reg GPIOB IDR`) to tell wiring from configuration.

### 2.3 — Superloop (`2.3-superloop`)

Step `00-homework-three-leds` on both boards: three LEDs at different rates from one clock read per pass, a pause
button, an interval button.

- **A pointer, not a copy:** `LED_type_t *led = &LEDS[i];` updates the array; `LED_type_t led = LEDS[i];` loses the
  update, and every LED toggles on every pass (dim and steady instead of blinking).
- **ESP-IDF has no toggle** and no pin setup for us: each LED keeps its own `level` (`gpio_get_level()` on an
  output-only pin reads 0); `gpio_reset_pin()`, `gpio_set_direction()`, `gpio_set_pull_mode()` are ours, where CubeMX
  writes `MX_GPIO_Init()`.
- **The Black Pill's KEY (PA0)** has only 330 Ω in series and no pull-up on the board: it needs the internal pull-up.
- **Known limits on both:** no debounce (a press sometimes counts twice); after a pause every LED that is due toggles
  at once. ESP32: the never-waiting loop starves IDLE0 and the task watchdog warns every 5 s (no reset).

### 2.4 — Hardware interrupts (`2.4-hardware-interrupts`)

Step `00-homework-button-debounce`: ESP32 = tasks 1–4, one commit per task; STM32 = task 3 + the teacher's extra
short / long press tasks.

- **Measured on the ESP32** (one run each, 10–11 presses): false triggers with no debounce 11 (21 interrupts),
  time-based 2, state-based 0, polling 0; the RC row is still empty.
- **A floating input counts by itself** (3099 → 3359 interrupts in 4 s); `gpio_reset_pin()` turns the internal pull-up
  on, so `GPIO_FLOATING` comes after it when only the external 10 kΩ should pull.
- **ESP-IDF compiles C as C23:** `void isr()` means `(void)`, so an ISR for `gpio_isr_handler_add()` must be
  `void isr(void *arg)`; `IRAM_ATTR` needs `esp_attr.h`; `%lu` for `uint32_t`. `vTaskDelay(pdMS_TO_TICKS(10))` in the
  loop silences the task watchdog.
- **STM32:** the callback's `GPIO_Pin` is a mask (`GPIO_PIN_5`), `== 5` never matches; EXTI runs above SysTick, so no
  `HAL_Delay()` inside it; PB5 is `TC` (3.3 V only), PB6 / PB7 are `FT`. Known limits: a tap under 30 ms counts as
  long; two microsecond-wide races between reading the timestamp and clearing the flag.

### 2.5 — Timers (`2.5-timers`)

Steps: `00-homework-exhaust-fan-esp32` (a relay as the fan) and the extra `01-homework-encoder-buzzer-stm32`.

- **GPTimer (ESP32):** `auto_reload_on_alarm` resets the counter in hardware, so the callback's entry delay doesn't
  drift; the callback only changes a variable (a `printf` there costs about 87 µs per character and takes locks);
  `1000000ULL` (one hour in µs overflows a 32-bit `int`); register the callbacks before `gptimer_enable`. ESP-IDF 6.1
  has only `driver/gptimer.h`. The task watchdog only logs unless `esp_task_wdt_reconfigure()` turns the panic on.
  The times are left at the 8 s / 2 s debug values.
- **Encoder (STM32):** TIM4 in encoder mode counts every edge in hardware; read `CNT` as `int16_t`, or one step down
  reads 65535. ARR and CCR are preloaded, so the loop can rewrite them any time; silence is CCR = 0.
- **A passive buzzer straight from a pin:** its coil measured 46.6 Ω, so 220 Ω in series (≈ 12 mA, under the 25 mA
  per pin); no transistor and no diode, the push-pull output always gives the coil current a path. The melody blocks
  the loop (`HAL_Delay`, about 19 s).

### 2.6 — Debounce with timers (`2.6-debounce-timers`)

Steps: `00-lecture-button-fsm-esp32` (the teacher's code, unchanged) and the extra `01-homework-button-fsm-esp32`.

- **The lecture's state machine** knows no pins and no clock: a 10 ms task (`xTaskDelayUntil`, no drift) gives it the
  level and the time; a level held 30 ms counts; SHORT (350 ms after the release), DOUBLE, LONG (2 s, while held),
  STUCK (7 s). The button is active high (pull-down, other leg to 3.3 V).
- **The homework:** six explicit states in a `switch` (no `default`, so `-Wswitch` catches a missing `case`) and one
  callback per event (`button_fsm_on()`). Register the callbacks after `button_fsm_init()`, which clears them. Built,
  not run on the board.
- **Pull-request lesson:** put a homework's starting code on `main` first (PR #25), so its PR shows only the changes.

## Known issues / open

1. STM32 versions in C++: CubeMX generates C. Works as planned since the 2.1 STM32 homework (PR #7): a C++ file of
   our own, called from a `USER CODE` block in `main.c`, in a project converted to C++ in CubeIDE (details in the 2.1
   notes). CubeIDE 2.2.0's C++ flags (arm-none-eabi-g++ 14.3.1): `-std=gnu++14 -fno-exceptions -fno-rtti
   -fno-use-cxa-atexit -Wall`. `static constexpr GPIO_TypeDef* kPort = GPIOC;` fails ("`reinterpret_cast` ... is not a
   constant expression"), while `constexpr uint16_t` for `GPIO_PIN_13` is fine. Still untested on the board: a
   `HAL_GPIO_EXTI_Callback` defined in a `.cpp` with the HAL's signature keeps its C name (test files), but one with
   another parameter type (`uint8_t`) compiles to a mangled name, so the HAL's empty `__weak` default stays and the
   button does nothing, with no error or warning.
2. CubeIDE itself builds with `-Wall` only; CI (`build-stm32.sh`) adds `-Wextra`, so check a step there or with the
   script locally before calling it warning-free.
