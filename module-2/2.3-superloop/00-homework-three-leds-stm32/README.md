# 00 — Homework: three LEDs in a non-blocking superloop on the STM32 (Black Pill)

The lesson 2.3 homework on the WeAct Black Pill (STM32F411CEU6): one `while (1)` loop blinks three LEDs at different
rates from `HAL_GetTick()`, without `HAL_Delay`. One button pauses all blinking, the other changes the interval of one
LED. Written in C inside the `USER CODE` blocks of CubeMX's `main.c`, starting from the lecture's code (the LED
struct and the loop over the array). The git history of this folder shows the work one change per commit.

## Assignment

"Additional homework" (the teacher's text in the LMS, translated in full):

- Make a non-blocking superloop where three LEDs blink at different frequencies.
- One button pauses all blinking.
- The second button changes the interval of one of them.
- Make the loop run in the minimal amount of time when none of the actions is needed.

## How each point is done

| Point | In the code (`Core/Src/main.c`) |
|---|---|
| Three LEDs, different frequencies, non-blocking | `LEDS[3]`, an array of `LED_type_t` (port, pin, `half_period`, `last_change_timestamp`): PC13 every 100 ms, PA2 every 250 ms, PA3 every 500 ms. Each pass takes one `HAL_GetTick()` and toggles an LED only when `now - last_change_timestamp >= half_period`; nothing in the loop waits |
| One button pauses all blinking | `BUTTON_2` (PA1, external button): each press flips `paused`, and while it is set the `for` over the LEDs runs no step, so every LED keeps the state it had (lit or dark) |
| The second button changes one LED's interval | `BUTTON_1` (PA0, the board's KEY): each press moves `LEDS[2].half_period` (PA3) to the next value, 500 → 250 → 100 → 500 ms; the other two LEDs keep their rates |
| Minimal loop time when nothing is due | see [The idle pass](#the-idle-pass) |

Both buttons count a press on the change from released (`GPIO_PIN_SET`) to pressed (`GPIO_PIN_RESET`), not while
held, and each has its own "previous level" variable, so a press on one never affects the other.

## The idle pass

When no button changed and no LED is due, one pass does only reads and comparisons:

- one `HAL_GetTick()` (reads a variable the SysTick interrupt increments);
- two `HAL_GPIO_ReadPin()` (each reads the port's `IDR` register);
- two edge checks, both false;
- three subtractions and comparisons in the `for`, all false.

No `HAL_Delay`, no pin write, no UART. The costly work (`HAL_GPIO_TogglePin`, changing an interval) runs only on the
pass where it is due. While paused the `for` does no step at all, so the pass is shorter still. The pass time itself
was not measured.

## Project

A CubeIDE project generated by CubeMX into this folder; our code lives only in the `USER CODE` blocks of
`Core/Src/main.c`, which a regenerate keeps.

| Pin | CubeMX setting | Used for |
|---|---|---|
| PC13 | GPIO output, push-pull, no pull; label `LED1` | the board's blue LED (3V3 → 1.5 kΩ → LED → PC13, lit on LOW) |
| PA2 | GPIO output, push-pull, no pull; label `LED_2` | LED through 220 Ω to GND |
| PA3 | GPIO output, push-pull, no pull; label `LED_3` | LED through 220 Ω to GND |
| PA0 | GPIO input, pull-up; label `BUTTON_1` | the board's KEY (PA0 → 330 Ω → GND, no pull-up on the board): changes PA3's interval |
| PA1 | GPIO input, pull-up; label `BUTTON_2` | button to GND: pause |
| PA13 / PA14 | SYS: Serial Wire | SWDIO / SWCLK for the ST-Link |
| PH0 / PH1 | RCC: HSE crystal | 25 MHz crystal |

**Clock:** HSE 25 MHz → PLL (M = 12, N = 96, P = 2) → SYSCLK 100 MHz. Time comes from SysTick's 1 ms
`HAL_GetTick()`. STM32Cube FW_F4 V1.28.3, CubeMX 6.18.1, CubeIDE 2.2.0.

PC13's LED and the KEY button are on the board. PA0 and PA1 read 1 while released and 0 while pressed.

## Notes

- **One timestamp per pass.** `HAL_GetTick()` is read once at the top of the pass, so all three LEDs are compared
  against the same moment.
- **A pointer, not a copy.** `LED_type_t* led = &LEDS[led_idx];` points at the array element itself, so
  `led->last_change_timestamp = ...` updates the array. `LED_type_t led = LEDS[led_idx];` would copy the 16-byte
  struct, the update would be lost, and every LED would toggle on every pass (dim and steady instead of blinking).
- **`LEDS[2].half_period`** uses `.`: `LEDS[2]` is the element itself; `->` is for a pointer.
- **The KEY needs the internal pull-up.** The board has only a 330 Ω resistor in series with the button; a released
  KEY without a pull-up leaves PA0 floating and reads at random.
- **The wrap of `HAL_GetTick()`.** `now - last >= half_period` with `uint32_t` stays right when the millisecond
  counter wraps after about 49.7 days.
- **No debounce (known limit).** A press sometimes counts twice (seen on the board with the pause button): the
  contacts bounce for a few milliseconds, and the loop is fast enough to see each bounce as a new press. The fix
  would be the 2.2 approach: accept a change of a button's level only 30 ms after its previous accepted change.
- **After a pause** the LEDs' timestamps are old, so every LED whose interval has passed toggles on the first pass
  after the pause ends; the rates are back to normal from the next toggle.

## Checked on the board

- Three LEDs blink at their three rates (step 1).
- PA1 freezes and resumes all blinking; sometimes a press toggles twice (bounce).

Build (Debug, `-O0 -g3`): 0 errors, 0 warnings with CubeIDE's flags and with `-Wextra`. `arm-none-eabi-size`: `text`
6168, `data` 64, `bss` 1576 bytes.

## Working with the step

- **Open:** in CubeIDE, File → Open Projects from File System → this folder (opened in place, not copied into the
  workspace).
- **Build:** Project → Build Project (the hammer).
- **Flash:** Run → Run As → STM32 C/C++ Application, with the ST-Link connected. Launch files (`*.launch`) hold
  absolute paths and are not committed, so the first Run creates one.
- **Change pins or the clock** in `00-homework-three-leds-stm32.ioc` with CubeMX, then regenerate: everything in
  `main.c` outside the `USER CODE` blocks is rewritten. Open the `.ioc` from this folder: a CubeMX window still
  holding an older copy of the project generates into that copy's path.
